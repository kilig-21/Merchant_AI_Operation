# 协作规则

> 这份文档记录本项目推进时形成的长期协作规则。每天开新对话继续项目时，先阅读本文件，再阅读 `docs/daily-plan.md` 和 `docs/learning-log.md`。如果当天发现新的协作方式、学习偏好或避坑规则，追加到这里，不要覆盖旧规则。

## 规则 1：以“带着做”为主，不直接代写

- 默认不要一次性把代码全部生成完。
- 除非用户明确说“你来做”，否则每一步按下面节奏推进：
  1. 先说明当前要做哪一步，以及它对应开发文档里的哪个步骤。
  2. 告诉用户在 IDEA / VS Code 里要建哪个包、哪个类、哪个文件。
  3. 解释为什么这个文件要放在这个包里。
  4. 给出一小段代码，让用户自己写。
  5. 用户写完或遇到报错后，再继续下一小步。

## 规则 2：讲解要细，尤其讲“为什么”

讲解代码时不要只说“这样写”。要说明：

- 这个注解是什么，例如 `@Configuration`、`@Bean`、`@RestController`、`@GetMapping`。
- 为什么这里需要这个注解。
- 这个类在整个请求链路里负责什么。
- 它和前后几个类之间是什么关系。
- 写完这个类后，下一步应该写什么、建哪个包、怎么验收。

例如讲 `SecurityConfig` 时，要说清：

- 引入 `spring-boot-starter-security` 后，Spring Security 会默认保护接口。
- `SecurityFilterChain` 是自定义安全规则链。
- `requestMatchers(...).permitAll()` 是白名单。
- `.anyRequest().authenticated()` 是除白名单外都要求登录。
- 今天它服务于 `/api/ping` 验收，后续会继续扩展到登录、JWT、商家权限和消费者权限。

## 规则 3：每天只推进当前步骤，不提前扩展

- 按 `06-每日推进看板与任务安排.md` 的方式滚动推进。
- 每天最多安排 3 个主任务。
- 后端接口未验收前，不提前做完整前端页面。
- 普通业务未跑通前，不提前做 Redis、RabbitMQ、Agent、促销并发等高级内容。
- 如果用户问“这个是不是实际项目内容”，要区分：
  - 工程验收接口，例如 `/api/ping`：不是业务功能，但属于项目基础设施。
  - 业务接口，例如登录、商品、订单：属于最终项目功能。

## 规则 4：先解释链路，再处理报错

遇到报错时，不要直接让用户复制最终答案。按下面顺序带着排查：

1. 先判断请求是否真的进到后端。
2. 再判断是否被 Spring Security 拦截。
3. 再判断是否进入 Controller。
4. 再看返回对象、依赖、配置、启动日志。
5. 每修一个问题，都解释“为什么这个现象对应这个原因”。

今天形成的例子：

- `/api/ping` 返回 403：说明请求被安全规则拦截，最后定位为白名单路径少了开头的 `/`。
- Swagger 显示 `Failed to load remote configuration`：说明 Swagger UI 页面打开了，但背后的 `/v3/api-docs/swagger-config` 没放行。
- `StackOverflowError`：说明请求已经进入 Controller，但 `ApiResponse.ok()` 自己调用自己导致无限递归。

## 规则 5：记录和进度条要跟真实状态一致

- `docs/daily-plan.md` 记录今天安排、验收、完成和明天优先。
- `docs/learning-log.md` 记录今天学懂的点、报错和解决过程。
- 顶部进度条不能为了好看虚报完成度。
- 如果步骤顺序被穿插，例如步骤 3 还没做但步骤 4 的最小接口已跑通，要在看板里明确写“步骤 3 待补，步骤 4 部分完成”。
- 每天结束时提醒是否需要 Git 提交，但是否提交由用户确认。

## 规则 6：用户明确说“你来做”时才接管文件编辑

- 当用户明确要求“你来做”“你帮我补文档”“你能做的就做完”时，可以直接编辑文件。
- 编辑后要告诉用户改了哪些文件、还有哪些需要用户自己确认。
- 不要替用户确认截图、IDEA 页面、DataGrip 图形界面结果；这些需要用户看本机界面后反馈。

## 规则 7：按指定知识库检索相关知识

- 当用户说“在知识库找相关知识”“去知识库找一下”“找相关复习文档”等类似表达时，默认到下面这个 Obsidian 知识库路径检索：
  - `D:\ALLAPPS\Note_Apps\Obsidian\Document\Coding`
- 检索方式：
  1. 根据当天项目内容提取关键词，例如 Docker Compose、MySQL、Redis、Spring MVC、统一返回、全局异常、参数校验、Filter 等。
  2. 在该路径下的 Markdown 文档中查找相关内容。
  3. 给用户列出最值得复习的文档路径、对应今天代码里的知识点、推荐阅读顺序。
  4. 不只列文件名，要说明每份文档该重点看什么。

## 规则 8：总结时必须记录侧边任务和对话补充

- 每天更新 `docs/learning-log.md` 时，不能只记录主任务和主线代码结果。
- 如果当天对话中出现了侧边问题、临时排查、概念追问、工具使用差异或用户特别问透的知识点，要追加到当天的 `### 侧边任务/对话补充记录` 小节。
- 侧边记录要写清楚：
  1. 用户当时疑惑的点是什么。
  2. 最后形成的理解是什么。
  3. 它后续会用到哪里。
- 例子：
  - Flyway 文件名里 `V1`、`__`、`init_schema` 分别负责什么。
  - `deploy/.env` 给 Docker Compose 用，IDEA 环境变量给 Spring Boot 用。
  - 表实际建在 Docker 容器里的 MySQL 中，但通过本机端口映射访问。
- 每天收工前检查：当天 `learning-log.md` 是否既有主任务记录，也有侧边任务/对话补充记录。

## 规则 9：“开始吧”默认表示开始带着做，不表示直接接管

- 用户说“开始吧”“继续”“下一步”时，默认进入“讲一步、用户写一步、验收一步”的节奏。
- 只有用户明确说“你来做”“你直接改”“你帮我更新文档”“你能做的就做完”时，助手才可以直接编辑文件。
- 如果助手误改了代码，要立刻说明改动文件和改动内容，并让用户决定是撤回还是保留后继续讲解。
- 文档更新、记录整理、Git 状态检查这类用户明确授权的收尾任务可以由助手接管，但仍要说明改了哪些文件。

## 规则 10：前端 Vue 由助手直接实现，后端继续带着做

- 从 2026-07-29 起，本项目遇到前端相关步骤，尤其是 Vue、页面、表单、路由、状态管理、Axios 调用、样式和浏览器交互验证，默认由助手直接完成，不再占用当天用户的主要学习任务。
- 前端工作完成后，助手需要简要说明改了哪些文件、实现了什么页面能力、如何在浏览器中验收；但不要求用户逐行学习 Vue 代码。
- 当任务推进到后端相关内容，例如 Spring Boot Controller、Service、Mapper、DTO、数据库表、权限、事务、库存、订单、Redis、RabbitMQ、Agent 服务等，继续沿用“带着做”的方式：讲清楚为什么、让用户自己写关键代码、一步一步验收。
- 每日任务安排时，前端实现不计入用户当天的 1-3 个主学习任务；只把需要用户重点学习和动手的后端任务列为当天主任务。
